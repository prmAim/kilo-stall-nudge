# Spec: Kilo-плагин «stall-nudge» (авто-продолжение при пустом ходе)

## Status

Draft — реализация в отдельном workspace.

## Проблема

Агентный цикл Kilo может вернуть **пустой финальный ход** сразу после результата инструмента. С точки зрения пользователя сессия после этого молчит: нет ни вывода, ни индикатора «работает / завис». Приходится вручную писать «продолжай». Неоднократно наблюдалось в `prizmaTorg` (паузы по несколько минут после backend/e2e-команд).

Корень — в цикле оркестрации (модель выдаёт пустой ход, и цикл ничего не эмитит), а не в доступе модели к инструментам. Пока идёт тишина, с нашей стороны **ничего не выполняется**, поэтому:

- ни один встроенный инструмент не может это заметить (они запускаются только по вызову);
- ни один MCP-сервер не может это заметить (MCP-инструменты пассивны, request/response).

Вывод: детекция и восстановление должны жить на уровне оркестратора — то есть это **Kilo-плагин**, а не MCP.

## Цели

1. Детектировать конкретный отказ: пришёл результат инструмента, а следующий ход ассистента пустой (или вообще не наступил в течение таймаута).
2. Автоматически пинать цикл продолжать, детерминированно восстанавливаясь из сохранённого состояния.
3. Ограничивать поведение (максимум «пинков») и делать его наблюдаемым.

## Не-цели

- Не MCP-сервер.
- Не хранилище памяти (состояние восстановления уже лежит в `.scratch/state.md` + `worklog.md`).
- Не смена модели.
- Не оценивает «правильно ли сделана работа» — только «замолчал ли цикл».

## Требования

### R1 — Детекция «замершего» хода
Зафиксировать, когда агент выдал пустой финальный месседж после результата инструмента, либо не выдал ничего в течение `idleTimeoutMs` (по умолчанию 180000) от последнего результата инструмента, пока ход ожидается.

### R2 — State-aware авто-пинок
При детекции отправить продолжение (синтетический user-месседж), который инструктирует модель:
- сначала прочитать `.scratch/state.md` и `.scratch/worklog.md`;
- продолжить с пункта «Next step»;
- дописать heartbeat в `worklog.md` перед следующим вызовом инструмента.

Промпт по умолчанию: «Продолжи с Next step из .scratch/state.md: сначала прочитай state.md и worklog.md, затем допиши heartbeat в worklog.md и выполни следующий шаг.»

### R3 — Ограничение поведения
- `maxNudges` (по умолчанию 3): после N пинков в одном эпизоде замирания прекратить пинать и перейти только в режим `alert`.
- Полностью остановиться при `.scratch/status.txt == DONE`.

### R4 — Режим алерта
Настраиваемый `onStall`: `nudge` (по умолчанию), `alert`, `both`. Alert = видимое уведомление в TUI + запись в `.scratch/plugin.log` (+ опциональный звуковой сигнал).

### R5 — Наблюдаемость
Логировать каждое детектирование и пинок: `[ts] STALL detected (age=Xs) → nudge #n` в `.scratch/plugin.log`. Показывать текущее состояние (armed/disarmed, счётчик пинков) в TUI.

### R6 — Opt-in и конфигурируемость
Выключен по умолчанию; включается через `kilo.json`. Все пороги/пинки/промпт конфигурируемы.

### R7 — Темп пинков (анти-re-stall)
После отправки пинка (или алерта) следующий stall не детектится раньше, чем через `idleTimeoutMs` с момента пинка: пришедший в этом окне `session.idle` подавляется и логируется как `→ skipped (cooldown)`. Ответ модели (текст или tool-call) сбрасывает кулдаун — дальше обычный цикл; тишина `idleTimeoutMs` → следующий пинок по таймеру.

Мотивация: боевой лог 2026-09-16 (`setupKiloCode/.scratch/plugin.log`) показывал re-stall через 0–7 с после пинка — бюджет `maxNudges` сгорал за секунды вместо паузы 180 с между пинками.

### R8 — Межпроцессная дедупликация пинков
Каждый процесс Kilo (TUI-сессия, VS Code extension serve) грузит плагин независимо, и все экземпляры пинают одну сессию дубликатами (в логе: два нуджа с интервалом 300 мс, три алерта за 2 с). Перед отправкой пинка или алерта экземпляр проверяет маркер `<stateDir>/nudge.marker` (timestamp + pid): если **другой** экземпляр действовал меньше `dedupWindowMs` (по умолчанию 60000) назад — действие пропускается с логом `→ skipped (recent nudge by another instance)`. Свой след экземпляр игнорирует: темп собственных пинков регулирует кулдаун R7. Дедупликация best-effort (миллисекундное окно между проверкой маркера и записью).

## Конфигурация (kilo.json)

```jsonc
{
  "plugin": ["kilo-stall-nudge"], // npm-пакет или file:// путь
  "stallNudge": {
    "enabled": true,
    "idleTimeoutMs": 180000,
    "maxNudges": 3,
    "onStall": "both", // nudge | alert | both
    "stateDir": ".scratch",
    "dedupWindowMs": 60000,
    "nudgePrompt": "Продолжи с Next step из .scratch/state.md ..."
  }
}
```

## Точки интеграции (проверить по Kilo plugin SDK)

- **Хук события**: колбэк на конец хода, получающий (a) был ли отложенный результат инструмента, (b) финальный текст ассистента (возможно пустой). Если `toolResultPending && finalText пуст` → запустить таймер замирания.
- **Модель исполнения таймера**: плагин должен жить внутри TUI-процесса и держать таймер на протяжении долгой сессии. Подтвердить, что хост плагинов не убивает плагин между ходами.
- **Отправка пинка**: метод SDK для программного добавления синтетического user-месседжа / повторного запуска цикла. Если SDK умеет только алертить (без инъекции ввода) — реализовать режим `alert` и задокументировать ограничение.
- **Чтение state-файлов**: плагину нужен доступ к файловой системе (или `kilo_memory_recall`), чтобы знать status/устаревание.

## Acceptance criteria

- [ ] AC1: сессия, вернувшая пустой ход после результата инструмента, детектируется в пределах `idleTimeoutMs`.
- [ ] AC2: плагин отправляет продолжение, и сессия возобновляется с `state.md` (наблюдаемо: следующий месседж ссылается на «Next step»).
- [ ] AC3: после `maxNudges` без прогресса плагин прекращает пинать и только алертит.
- [ ] AC4: при `status.txt == DONE` плагин не пинает никогда.
- [ ] AC5: каждое детектирование/пинок логируется в `.scratch/plugin.log`.
- [ ] AC6: выключен по умолчанию; включается только конфигом.
- [ ] AC7: работает на Windows (PowerShell) с сетапом `prizmaTorg`; задокументирован для POSIX.
- [ ] AC8: немедленный `session.idle` после пинка не приводит ко второму пинку раньше `idleTimeoutMs` с момента первого (кулдаун R7).
- [ ] AC9: два экземпляра плагина на одном каталоге: второй скипает действие, пока след первого свежий (< `dedupWindowMs`), и снова действует после остывания (R8).
